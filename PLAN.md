## 0. Что это

**CryptoSwap** — обменник валют: фиат → крипта, крипта → фиат, крипта → крипта.
Пользователь выбирает валюту "отдаю" и валюту "получаю", вводит сумму, видит курс
и итоговую сумму к получению (с учётом комиссии), может создать заявку на обмен.

**Важно: это НЕ реальный обменник с реальными деньгами.** Это демонстрационный
портфолио-проект — заявки создаются, курсы реальные (публичное API), но фактического
перевода средств не происходит (нет интеграции с реальными платёжными провайдерами/
крипто-кошельками с приватными ключами). Это должно быть явно и честно написано в
README и, если есть смысл, в UI (баннер, как в PulseOps: "Demo — no real funds move").

**Портфолио-цель:** отдельный проект от PulseOps (другой домен: не SaaS-аналитика,
а финтех/обменник), чтобы показать широту. Одна четкая история, не смешивать с
другими проектами.

## 1. Легенда / позиционирование (придумать так же честно, как в PulseOps)

Перед началом реализации определить и вписать в README:
- **Что это:** свой pet/MVP-проект обменника (аналог small crypto exchanger типа
  простых сайтов-агрегаторов курсов).
- **Для кого:** обычные пользователи, которым нужно быстро прикинуть курс обмена
  фиат↔крипта или крипта↔крипта без захода на биржу.
- **Проблема:** курсы разбросаны по разным сайтам/биржам, нет единого удобного
  калькулятора с историей заявок.
- **Решение:** один экран — выбрал валюты, увидел живой курс и сумму, создал заявку
  (демо, без реального перевода денег).
- **Твоя роль:** соло — продукт, дизайн, фуллстек.

НЕ выдумывать реального работающего биттех-бизнеса с реальными объёмами/клиентами —
это создаст регуляторные вопросы на собеседовании (обмен крипты требует лицензий
в реальном мире). Чётко: "pet-проект/MVP, демонстрирует техническую реализацию
конвертера, без реальных переводов денег".

## 4. Источник данных о курсах (ключевой технический вопрос)

Нужны два типа курсов:
1. **Фиат↔фиат / фиат↔крипта** курсы
2. **Крипта↔крипта** курсы

### Рекомендуемые бесплатные API (проверить актуальность на момент реализации,
### у всех есть free tier):

- **CoinGecko API** (`api.coingecko.com`) — бесплатно, без API-ключа для базовых
  запросов, даёт курсы крипты к фиату и крипты к крипте (через фиат-мост).
  Простой и надёжный вариант для старта — **рекомендуется как основной источник**.
- **exchangerate-api.com** или **Frankfurter API** (frankfurter.dev, бесплатно,
  без ключа) — для чистых фиат↔фиат курсов, если нужны отдельно от крипты.
- **CoinMarketCap API** — тоже есть free tier, альтернатива CoinGecko.

**Архитектурное решение:** курсы запрашивать на **сервере** (API route/Route
Handler), не с клиента напрямую — чтобы (а) спрятать API-ключ, если он нужен,
(б) закэшировать на несколько секунд/минут и не упираться в rate-limit,
(в) держать единую точку, откуда UI берёт данные (легко подменить провайдера).

Пример потока:
```
Клиент → GET /api/rates?from=BTC&to=USD → сервер идёт в CoinGecko (с кэшем
in-memory/Redis на ~30-60 сек) → возвращает { rate, updatedAt }
```

Курс "крипта → крипта" считать через кросс-курс к общей базовой валюте (USD):
`rate(A→B) = rate(A→USD) / rate(B→USD)`.

## 5. Доменная логика (то, что тестируется на 100%, по аналогии с PulseOps)

Вынести в чистые функции без побочных эффектов (легко покрыть Vitest):

```
computeExchangeAmount(input: {
  amount: number;
  direction: "give" | "receive"; // с какой стороны введена сумма
  rate: number;        // курс "отдаю"→"получаю", по данным API
  feePercent: number;  // комиссия обменника, например 1.5
}): {
  giveAmount: number;
  receiveAmount: number;
  feeAmount: number;
  effectiveRate: number; // курс с учётом комиссии
}
```

```
computeCrossRate(rateAtoUSD: number, rateBtoUSD: number): number
// курс A→B через общую базу USD
```

```
validateExchangeRequest(input): { valid: boolean; errors: string[] }
// валидация суммы (мин/макс лимиты), валют (пара поддерживается), и т.д.
```

Эти функции — ядро приложения. Именно они должны быть покрыты тестами на 100%,
аналогично `computeAnalytics`/`computeMrrMovement`/`computeCohortRetention` в
PulseOps. UI и API routes — тонкий слой поверх них.

## 13. Современный дизайн-стиль (референсы + design system)

Референсы (изучены через выдержки/структуру страниц, где не было прямого
визуального доступа — импровизация на основе общих паттернов этих
продуктов):
- **MoonPay** (`/buy`) — модульные карточки, пошаговый флоу покупки,
  крупные CTA-кнопки, ряд логотипов платёжных систем как визуальное
  подтверждение доверия, карусель отзывов.
- **Changelly** (`/buy/btc`), **CoinGate** (`/buy`) — простой калькулятор
  на первом экране: два поля (отдаю/получаю), явный курс, минимум лишних
  элементов, быстрый переход к действию.
- **Topper**, **Simplex** — светлые, воздушные формы, скруглённые крупные
  поля ввода, дружелюбная типографика, акцент на простоте одного экрана.
- **Crypto.com** — крупные заголовки-хиро, высокий контраст, карточная
  структура, акцентные градиенты на кнопках, ощущение масштаба/доверия
  через цифры (кол-во пользователей и т.п. — в нашем демо-проекте не
  применимо буквально, но сам приём "крупная цифра = доверие" переносим
  на крупный курс обмена).

**Вывод: калькулятор должен быть один экран-виджет** (как у Changelly/
CoinGate), но визуально оформлен на уровне MoonPay/Crypto.com — с крупной
карточкой, мягкими тенями, градиентами и внятной иерархией, а не просто
формой с бордерами.

**Design system (обновляет раздел 12, применяется в `globals.css` +
компонентах):**
- **Форма:** крупные скругления (`rounded-2xl`/`rounded-3xl`) вместо
  острых углов, мягкие многослойные тени (`shadow-lg`/`shadow-black/20`)
  вместо тонких бордеров как основного разделителя.
- **Фон:** в тёмной теме — не плоский чёрный, а лёгкий радиальный
  градиент/vignette (тёмно-серый → почти чёрный) за карточкой калькулятора,
  чтобы карточка "парила" (как hero-секции MoonPay/Crypto.com). В светлой
  теме — мягкий светло-серый/кремовый фон с едва заметным золотым glow.
- **Акценты и CTA:** главная кнопка — золотой градиент
  (`linear-gradient(135deg, gold-light, gold-mid, gold-dark)`) с лёгким
  подъёмом/тенью при hover, а не плоская заливка `--accent`.
- **Курс обмена — главный визуальный элемент:** крупная типографика для
  суммы "к получению" (по аналогии с тем, как Crypto.com/MoonPay делают
  акцент на крупных цифрах), а не мелкий текст в списке.
- **Карточка калькулятора:** двойной блок "Отдаю / Получаю" с крупными
  полями ввода, разделённый кнопкой swap (⇅) в виде круглой кнопки со
  сдвигом на границу блоков (визуальный приём из Changelly/CoinGate).
- **NavBar:** `sticky` + полупрозрачный фон с `backdrop-blur` (стеклянный
  эффект, как в современных фин-тех лендингах), лого + название слева,
  переключатель темы справа.
- **Demo-баннер:** не блеклая плашка, а золотая "pill"-плашка с иконкой —
  привлекает внимание, но не выглядит как предупреждение об ошибке.
- **Типографика:** сохраняется текущий Geist Sans, но с более выраженной
  иерархией размеров (крупный `text-3xl`/`text-4xl` заголовок, чёткий
  `text-sm text-muted` для второстепенного текста).
- **Респонсивность:** карточка калькулятора остаётся `max-w-md`, но с
  большими отступами и "воздухом" на десктопе (либеральный `py`/`gap`),
  как на референсных лендингах, а не плотная форма.

Компоненты, которые обновляются под этот стиль: `globals.css` (токены,
фон), `nav-bar.tsx`, `demo-banner.tsx`, `exchange-calculator.tsx`,
`currency-select.tsx`.

### 13.1 Бегущая строка курсов (rates ticker)

Приём, знакомый по биржам и обменникам (и явно нравящийся заказчику):
горизонтальная «бегущая строка» с курсами, идущая под шапкой сайта.
Делает страницу живой и сразу показывает, что курсы настоящие.

Требования:
- **Реальные данные, не заглушка** — строка питается тем же серверным
  слоем курсов, что и калькулятор (CoinGecko + Frankfurter через
  in-memory кэш), новый Route Handler `GET /api/ticker`, отдающий список
  `{ code, name, usdPrice, change24h }` по всем поддерживаемым валютам.
  Для крипты 24-часовое изменение берётся у CoinGecko
  (`include_24hr_change=true`), для фиата — не показывается либо считается
  как изменение к USD (если провайдер даёт исторические данные).
- **Автообновление** на клиенте раз в ~60 сек (совпадает с TTL кэша на
  сервере, лишние запросы к провайдеру не идут).
- **Внешний вид:** непрерывная прокрутка CSS-анимацией
  (`@keyframes marquee` + дублированный список для бесшовной петли), без
  JS-цикла; на hover анимация замирает (`animation-play-state: paused`),
  чтобы можно было прочитать цифры; по краям — маска-градиент
  (`mask-image`), чтобы элементы плавно «растворялись», а не обрезались.
- **Каждый элемент строки:** тикер валюты, цена в USD, и 24h-изменение
  зелёным/красным со стрелкой вверх/вниз (нейтральный цвет, если данных
  нет). Разделители между элементами — тонкая точка/линия в золотом цвете
  бренда.
- **Доступность:** `prefers-reduced-motion` отключает прокрутку (строка
  становится статичным горизонтально-скроллящимся списком).
- Файлы: `src/app/api/ticker/route.ts`, `src/components/rates-ticker.tsx`,
  анимация в `globals.css`; строка встраивается в `layout.tsx` под
  `NavBar`.

**Wow-эффект строки (не просто текст, а «живые» элементы):**
- Каждая валюта — «стеклянная» пилюля (`rounded-full`, полупрозрачный фон,
  `backdrop-blur`, тонкий бордер), а не голый текст.
- У каждой валюты — своя иконка: круглый значок с градиентом в
  фирменных цветах монеты (BTC — оранжевый, ETH — синий, SOL —
  фиолетово-зелёный и т.д.) и символом валюты (₿, Ξ, ₮, ◎, $, €, ₽).
  Реализуется своим компонентом `currency-icon.tsx` инлайн (без внешних
  картинок — CSP-безопасно, не зависит от сторонних CDN и не требует
  настройки `next/image` под внешние домены).
- **Реакция на hover каждой валюты:** пилюля приподнимается и
  подсвечивается золотым свечением (`box-shadow`), бордер становится
  акцентным, иконка увеличивается и слегка поворачивается, цена из
  приглушённой становится контрастной. Вся строка при этом замирает
  (`animation-play-state: paused`), чтобы курсор не «убегал» от элемента.

### 13.3 Композиция главного экрана (широкие экраны)

Проблема узкой центральной колонки: на десктопе по бокам остаётся пустое
поле — это выглядит устаревше. Решение — **двухколоночный hero**
(как на лендингах MoonPay/Crypto.com):

- **Слева** — текстовый блок: бейдж «Live market rates», крупный
  заголовок, подзаголовок, список преимуществ (прозрачная комиссия, живые
  курсы, без регистрации) с иконками, и визуальный «якорь» бренда —
  полный логотип (`logo-full.png`) с мягким золотым свечением позади.
- **Справа** — карточка калькулятора (главное действие), приподнятая
  тенью, шириной ~420–480px.
- На `lg` и шире — сетка `lg:grid-cols-2` с выравниванием по центру по
  вертикали и общим `max-w-6xl`; на мобильных — обычная одна колонка,
  калькулятор идёт первым по важности.
- Фон широких экранов не остаётся плоским: декоративные золотые
  радиальные свечения (`blur-3xl`, низкая прозрачность,
  `pointer-events-none`) по углам, чтобы «боковины» не читались пустыми.

### 13.4 Кастомные дропдауны и адаптив

Нативный `<select>` рисуется операционной системой и не поддаётся
стилизации — на фоне остальных полей он выглядит чужеродно. Замена:
собственный компонент по паттерну **listbox** (`select-menu.tsx`):
- триггер выглядит и ведёт себя как остальные инпуты (та же рамка,
  радиус, фокус-кольцо), внутри — иконка валюты, тикер и название;
- выпадающий список — карточка с тенью, скруглениями, галочкой у
  выбранного пункта и подсветкой активного;
- клавиатурный контракт эквивалентен нативному: стрелки, Home/End,
  Enter/Space, Escape, посимвольный type-ahead; фокус остаётся на триггере,
  активный пункт объявляется через `aria-activedescendant` (WCAG 4.1.2);
- закрытие по клику вне и по Tab.

**Адаптив (проверить на 320–420px):**
- Шапка: подпись «live rates · demo» скрывается ниже `sm`, лого и отступы
  уменьшаются, название усекается. Сами ссылки ниже `sm` уезжают в
  **бургер-меню**: кнопка с `aria-expanded`/`aria-controls`, выпадающая
  панель под шапкой, закрытие по Escape (с возвратом фокуса на кнопку),
  по клику вне и по переходу на ссылку. Переключатель темы остаётся в
  шапке — он нужен в один тап. В дереве доступности одновременно видна
  только одна навигация: панель скрыта атрибутом `hidden`, десктопная —
  через `display: none`.
- Табы операций: ниже брейкпоинта `xs` (26rem) перестраиваются в сетку
  2×2; скользящий индикатор при этом прячется (одна дорожка не может
  следовать за элементами в двух рядах), а активная вкладка получает
  собственную золотую заливку.
- Таблица `/rates`: горизонтальная прокрутка в своём контейнере, название
  валюты переносится под тикер на узких экранах.

### 13.5 Клик по валюте в бегущей строке → страница валюты

Сейчас пилюли в бегущей строке реагируют на hover, но некликабельны —
пользователь ожидает перехода, а его нет. Каждая пилюля становится ссылкой
на `/rates/[code]` (например `/rates/BTC`).

**Что показывает страница валюты (`/rates/[code]`):**

1. **Шапка валюты** — крупная иконка, тикер, полное название, тип
   (fiat/crypto).
2. **Hero-цена** — текущая цена в USD крупным кеглем (пропорциональные
   цифры, не `tabular-nums` — по правилам dataviz для крупных чисел) и
   рядом изменение за 24 часа со стрелкой и цветом.
3. **График истории** — переиспользуется существующий `RateChart`
   (`CODE → USD`) с пресетами 7/30/90 дней, crosshair и табличным дублем.
   Никакого нового кода для графика не требуется.
4. **Ключевые цифры за период** — минимум, максимум и изменение за
   выбранный диапазон. Считается чистой функцией над уже загруженной
   серией (`seriesStats`), покрывается тестами.
5. **Быстрый переход к обмену** — кнопки «Buy BTC» / «Sell BTC»
   (для фиата — «Exchange USD»), которые ведут на калькулятор с
   предзаполненной парой и нужным режимом. Реализуется через query-
   параметры (`/?mode=buy&receive=BTC`), которые калькулятор читает при
   инициализации состояния.
6. **Таблица кросс-курсов** — сколько стоит 1 BTC в каждой другой
   поддерживаемой валюте (считается из уже имеющихся USD-курсов через
   `computeCrossRate`, без новых запросов к провайдерам).
7. **Крошки** — `Calculator → Live rates → BTC`, с JSON-LD, как и на
   остальных внутренних страницах.

**Доступность и поведение:**
- Пилюля превращается в `<Link>`: цель ≥ 24px (2.5.8), видимый фокус,
  доступное имя вида «Bitcoin, $63,972, down 0.03% — view details».
- Прокрутка строки замирает не только на hover, но и **на фокусе с
  клавиатуры** (`:focus-within`), иначе до ссылки невозможно доехать
  табом — она уезжает из-под курсора.
- Дубликат списка (вторая копия для бесшовной петли) уже помечен
  `aria-hidden`; его ссылки дополнительно получают `tabIndex={-1}`, чтобы
  не было двойного обхода по табу.
- На `/rates` строки таблицы тоже становятся ссылками на ту же страницу —
  один и тот же пункт назначения из двух мест.

### 13.6 Единая ширина контента (layout-система)

Проблема: ширины разъехались по мере роста проекта — шапка и баннер
`max-w-5xl`, главная `max-w-6xl`, `/rates` и страница валюты `max-w-2xl`,
история, чекаут и страницы ошибок `max-w-xl`, плюс разные горизонтальные
отступы (`px-5` против `px-4 sm:px-5` в шапке). При переходе между
страницами контент прыгает и не выравнивается по шапке — ощущение, что это
разные приложения.

Решение — **две ширины, и обе задаются одним компонентом**
(`components/layout/page-container.tsx`), а не расставляются вручную:

| Вариант | Ширина | Где |
|---|---|---|
| `frame` | `max-w-5xl` | шапка, демо-баннер, бегущая строка, двухколоночный hero главной |
| `content` | `max-w-2xl` | все внутренние страницы: `/rates`, `/rates/[code]`, `/history`, все шаги чекаута, статус заявки, 404/ошибка/загрузка |

Правила:
- Горизонтальные отступы **одинаковые везде**: `px-4 sm:px-5` — те же, что
  в шапке, иначе контент не выравнивается с логотипом по левому краю.
- `max-w-6xl` на главной убирается: hero выравнивается по шапке
  (`max-w-5xl`), чтобы левый край заголовка совпадал с логотипом.
- Узкие карточки (форма чекаута) не сужаются отдельным `max-w-xl` —
  вместо этого ширину ограничивает сама карточка внутри общей колонки,
  а контейнер остаётся общим.
- Новый экран не задаёт ширину сам — он оборачивается в `PageContainer`.

### 13.2 Анимации интерактивных элементов (состояния)

Единый набор правил, чтобы интерфейс ощущался отзывчивым и дорогим, а не
дёргался. Все переходы — на `transform`/`opacity`/`box-shadow`
(GPU-friendly), длительности короткие, кривые — плавные.

- **Тайминги:** 150–200 мс для мелких элементов (ссылки, иконки, поля),
  250–300 мс для крупных (карточки, кнопки, пилюли). Кривая —
  `cubic-bezier(0.4, 0, 0.2, 1)` (ease-out), для «упругих» элементов
  (swap-кнопка) — лёгкий overshoot.
- **Состояния для каждого интерактивного элемента:**
  - `hover` — подъём (`-translate-y-0.5`), усиление тени, акцентный бордер;
  - `active` — возврат вниз/сжатие (`scale-95`), чтобы нажатие
    чувствовалось физически;
  - `focus-visible` — золотое кольцо (`ring-2 ring-accent/25`), никогда не
    убирать outline без замены (доступность с клавиатуры);
  - `disabled` — `opacity-45` + `pointer-events-none`, без анимаций;
  - `loading` — спиннер/скелетон вместо резкой подмены контента.
- **Главная CTA-кнопка:** золотой градиент, при hover — подъём и более
  насыщенная тень акцентного цвета, при active — обратно вниз.
- **Swap-кнопка (⇅):** круглая, при hover увеличивается (`scale-110`),
  при клике — поворот на 180° (визуально «переворачивает» пару).
- **Смена курса/суммы:** значение не должно резко «прыгать» — при
  обновлении курса делается короткая подсветка/fade нового значения, чтобы
  пользователь заметил изменение (но без мерцания при каждом рендере).
- **Карточки истории:** при hover — подъём + акцентный бордер + тень,
  создаёт ощущение «кликабельного объекта».
- **Появление контента:** мягкий `fade-in`+небольшой подъём для основной
  карточки и элементов истории при первом рендере, без длинных задержек.
- **Уважение к `prefers-reduced-motion`:** все декоративные анимации
  (бегущая строка, появление, подъёмы) отключаются/сводятся к смене цвета.

## 14. Операции: переключатель режимов (Buy / Sell / Swap / …)

Сейчас калькулятор — один универсальный режим «отдаю / получаю». На реальных
обменниках (MoonPay, Changelly, CoinGate, Simplex) вверху виджета стоит
переключатель операции — это сразу объясняет пользователю, что он делает, и
позволяет подстроить форму под сценарий.

### 14.1 Базовые режимы (делать в первую очередь)

| Режим | Что значит | Что меняется в UI |
|---|---|---|
| **Buy** | фиат → крипта | «Отдаю» ограничено фиатом, «Получаю» — криптой; поле реквизитов = адрес кошелька; сумма вводится в фиате |
| **Sell** | крипта → фиат | зеркально: «Отдаю» — крипта, «Получаю» — фиат; поле реквизитов = банковские данные (демо) |
| **Swap** | крипта → крипта | оба селектора только крипта; поле реквизитов = адрес кошелька получателя |

Реализация: режим — состояние калькулятора, которое **фильтрует списки
валют** и подпись поля реквизитов. Доменная логика расчёта
(`computeExchangeAmount`) не меняется — режим влияет только на то, какие
пары допустимы, поэтому проверку «пара соответствует режиму» логично
добавить в `validateExchangeRequest` (чистая функция → покрывается тестами
на 100%, как остальное ядро).

**UI переключателя:** сегментированный контрол (segmented control) —
горизонтальная группа из 3 пилюль в общей «дорожке» со скользящим золотым
индикатором активного режима (плавный `transform`, в духе раздела 13.2).
Полноценно доступен с клавиатуры (`role="tablist"`, стрелки влево/вправо),
на мобильных — на всю ширину карточки.

### 14.2 Что ещё можно добавить (предложения, по приоритету)

1. **Exchange (фиат → фиат)** — 4-й режим, дешёвый в реализации: курсы фиата
   уже есть от Frankfurter, отдельная логика не нужна. Логично, если
   позиционировать проект и как конвертер валют.
2. **Rate alert** («сообщить, когда курс достигнет X») — уже намечен в
   разделе 2.2. Это не операция обмена, поэтому лучше не в тот же
   переключатель, а отдельной кнопкой/вкладкой рядом с курсом.
3. **Recurring buy** (регулярная покупка, как у MoonPay) — сильный
   портфолио-приём: показывает работу с расписанием и повторяющимися
   сущностями. В демо-режиме — просто сохранённое «расписание» без реального
   исполнения.
4. **Limit order** («обменять, когда курс станет X») — интересная доменная
   логика (сравнение целевого курса с текущим), но требует фонового
   процесса/крона, что выходит за рамки MVP без бэкенда. Кандидат на
   итерацию 2.
5. **Sandbox/«Try with demo balance»** — виртуальный баланс, чтобы
   пользователь мог «покупать» без ввода реквизитов. Честно вписывается в
   демо-природу проекта и убирает трение на первом экране.

**Рекомендация:** сделать Buy / Sell / Swap (14.1) + Exchange как самый
дешёвый четвёртый режим; остальное — после, чтобы не размывать один
понятный сценарий.

## 15. Многошаговый флоу оплаты (после создания заявки)

Сейчас заявка создаётся и сразу попадает на страницу статуса. Нужен
пошаговый флоу, как у настоящих обменников.

### 15.1 Шаги

1. **Калькулятор** (`/`) — как сейчас, создаёт заявку.
2. **Метод оплаты** (`/exchange/[id]/method`) — выбор способа: карта,
   банковский перевод, крипто-кошелёк (депозит), а также «демо-баланс»
   (мгновенно, без реквизитов).
3. **Реквизиты** (`/exchange/[id]/details`) — форма зависит от метода:
   - карта → номер/срок/CVC (демо-значения);
   - банковский перевод → IBAN/имя получателя;
   - крипто → адрес кошелька, куда пользователь получит средства;
   - демо-баланс → шаг пропускается.
4. **Подтверждение** (`/exchange/[id]/confirm`) — сводка (сумма, курс,
   комиссия, метод, замаскированные реквизиты), таймер фиксации курса и
   кнопка «Confirm & pay». Для карты после подтверждения — имитация
   **3-D Secure/OTP** (любой код проходит, о чём явно написано). Для
   крипто-метода вместо OTP — экран **депозитного адреса с QR** и таймером.
5. **Статус** (`/exchange/[id]`) — анимированный трекер стадий:
   `awaiting payment → payment received → exchanging → sending → completed`
   с искусственными задержками и фейковым TX-хешем.

Все три варианта финала (подтверждение+трекер, OTP, депозитный адрес+QR)
не взаимоисключающие — они выбираются в зависимости от метода оплаты.

### 15.2 Управление шагами (защита от перескока)

Источник истины — **поле `step` внутри самой заявки** (сохраняется в
localStorage сейчас и в БД позже), а не URL:

```ts
type ExchangeStep = "method" | "details" | "confirm" | "otp" | "deposit" | "status";
```

- У каждого шага есть порядковый индекс. При заходе на URL шага
  сравниваем его индекс с индексом сохранённого `step`:
  - индекс URL **больше** сохранённого → редирект на актуальный шаг
    (перескочить вперёд нельзя);
  - индекс URL **меньше или равен** → показываем (назад ходить можно, чтобы
    поправить метод/реквизиты);
  - заявки с таким id нет → страница «not found».
- Логика сравнения — чистая функция (`resolveStepAccess`) в доменном слое,
  покрывается тестами вместе с остальным ядром.
- Прогресс-индикатор (1-2-3-4) виден на всех шагах, пройденные шаги
  кликабельны, будущие — нет.

### 15.3 Безопасность демо (никаких реальных переводов)

Ключевое требование: должно **выглядеть** как реальная оплата, но
пользователь физически не может отправить деньги.

- **Никаких реальных платёжных интеграций** — форма ничего не отправляет на
  внешние сервисы, данные остаются в localStorage браузера.
- **Карта:** поле предзаполнено общеизвестным тестовым номером
  (`4242 4242 4242 4242`), ввод реальных данных не требуется и явно не
  нужен; сохраняем только последние 4 цифры, никогда — CVC.
- **Крипто-депозит:** адрес намеренно **невалидный** (содержит
  `DEMO`-префикс и не проходит проверку контрольной суммы), поэтому
  кошелёк пользователя откажется по нему отправлять. QR кодирует
  текстовую строку-предупреждение, а не платёжный URI.
- **Банковский перевод:** реквизиты помечены как демонстрационные, IBAN не
  принадлежит реальному счёту.
- На каждом платёжном шаге — заметная плашка «Demo — no real payment is
  processed», в дополнение к глобальному баннеру.

## 16. Доступность (WCAG 2.2, уровни A и AA)

Цель — соответствие **WCAG 2.2 уровня AA** (включает все критерии уровня A).
Для портфолио это сильный сигнал: показывает, что автор думает не только о
красоте, но и о том, что интерфейсом реально можно пользоваться.

### 16.1 Что нужно исправить/обеспечить

**Уровень A:**
- **1.1.1 Non-text Content** — у всех иконок либо `aria-hidden` (если рядом
  есть текст), либо текстовая альтернатива. Декоративный QR уже помечен как
  «not scannable» через `aria-label`.
- **1.3.1 Info and Relationships** — семантическая разметка: `<nav>`,
  `<main>`, списки для перечислений, `<dl>` для пар «поле → значение»,
  корректная иерархия заголовков (на каждой странице ровно один `<h1>`).
- **1.4.1 Use of Color** — цвет не единственный носитель смысла: рост/падение
  в бегущей строке дублируются стрелками, статусы — иконками и текстом.
- **2.1.1 Keyboard** — весь флоу проходится с клавиатуры; segmented control
  режимов работает стрелками (`role="tablist"`).
- **2.2.1 Timing Adjustable** — таймеры (фиксация курса, окно депозита) не
  должны блокировать пользователя: по истечении даётся явное действие
  «обновить котировку», а сам таймер можно продлить.
- **2.2.2 Pause, Stop, Hide** — **критично для бегущей строки**: анимация
  идёт дольше 5 секунд и запускается автоматически, поэтому нужна видимая
  кнопка паузы (одного `:hover` недостаточно — с клавиатуры и на тач-экране
  он недоступен).
- **2.4.1 Bypass Blocks** — ссылка «Skip to content» в начале страницы,
  видимая при фокусе.
- **2.4.2 Page Titled** — у каждого роута свой осмысленный `<title>`.
- **3.3.1 Error Identification** — ошибки форм объявляются
  ассистивным технологиям (`role="alert"`), поле помечается `aria-invalid`
  и связывается с текстом ошибки через `aria-describedby`.
- **4.1.2 Name, Role, Value** — у всех контролов доступное имя; состояние
  передаётся через `aria-selected`/`aria-checked`/`aria-current`.

**Уровень AA:**
- **1.4.3 Contrast (Minimum)** — контраст текста ≥ 4.5:1 (крупного ≥ 3:1).
  Проверить приглушённый текст (`--muted`) и золотой акцент в обеих темах;
  при необходимости затемнить золото для светлой темы.
- **1.4.11 Non-text Contrast** — границы полей, иконки и индикатор фокуса
  ≥ 3:1 к фону.
- **1.4.10 Reflow / 1.4.4 Resize Text** — вёрстка не ломается при 200%
  масштабе и на узких экранах (уже отчасти обеспечено адаптивной сеткой).
- **2.4.7 Focus Visible** — видимый индикатор фокуса у **каждого**
  интерактивного элемента (сейчас есть не везде — добить ссылки в шапке,
  элементы бегущей строки, ссылки в истории).
- **2.4.11 Focus Not Obscured** — залипающая шапка не должна перекрывать
  сфокусированный элемент → `scroll-margin-top` у якорных целей.
- **2.5.8 Target Size (Minimum)** — интерактивные цели не меньше 24×24 CSS-
  пикселей.
- **3.2.3/3.2.4 Consistent Navigation & Identification** — шапка, крошки и
  прогресс шагов выглядят и ведут себя одинаково на всех экранах.

### 16.2 Хлебные крошки со schema.org

Крошки нужны и как навигация (пользователь видит, где он в многошаговом
флоу), и как разметка для поисковиков.

- Компонент `breadcrumbs.tsx`: `<nav aria-label="Breadcrumb">` со списком
  `<ol>`, текущий элемент помечен `aria-current="page"` и не является
  ссылкой.
- **Структурированные данные schema.org** — `BreadcrumbList` в формате
  **JSON-LD** (рекомендованный Google формат) внутри `<script
  type="application/ld+json">`: массив `itemListElement` из `ListItem` с
  полями `position`, `name`, `item` (абсолютный URL).
- Крошки показываются на внутренних страницах: `Home → History`,
  `Home → History → Request → <шаг>`. На главной не показываются (там
  крошка была бы единственной и бессмысленной).
- Так как страницы клиентские, JSON-LD рендерится тем же компонентом; для
  абсолютных URL берётся `NEXT_PUBLIC_SITE_URL` с безопасным фолбэком на
  текущий origin.
